# /report-issue

## 목적
시스템 사용 중 발견된 문제, 개선 아이디어, 새 기능 요청을 GitHub Issue로 등록합니다.
모든 개선은 Issue → Branch → PR → Merge 워크플로우를 따릅니다.

## 실행 주체
메인 세션 (오케스트레이터) — 문제/개선 아이디어를 구조화하여 GitHub Issue로 등록합니다.

## 입력
- 사용자의 문제 설명 또는 개선 아이디어
- 관련 커맨드/파일 경로 (있으면)

## 실행 절차
1. 이슈 유형 분류:
   - `bug` — 커맨드가 의도와 다르게 작동
   - `enhancement` — 기존 커맨드/설정 개선
   - `feature` — 새 커맨드/기능 요청
   - `docs` — 문서/가이드 보완

2. 이슈 내용 구조화:
   ```
   ## 현재 상태
   (무엇이 문제인지 / 무엇이 부족한지)

   ## 기대 상태
   (어떻게 되어야 하는지)

   ## 재현 방법 (bug인 경우)
   (어떤 커맨드를 어떤 조건에서 실행했는지)

   ## 관련 파일
   (영향받는 commands/, config/, scripts/ 파일)

   ## 제안 해결 방향
   (있으면)
   ```

3. `gh issue create` 로 GitHub Issue 생성:
   - 제목: `[{유형}] {요약}`
   - 라벨: bug / enhancement / feature / docs
   - 본문: 위 구조

4. 즉시 수정 가능한 이슈면:
   → "바로 수정할까요? /fix-issue {번호} 로 PR을 만들 수 있습니다" 제안

## 출력
- GitHub Issue URL 출력
- config/evolution-log.md에 이슈 번호 + 요약 기록

## 규칙
- 중복 이슈 체크 (`gh issue list`로 기존 이슈 확인)
- 이슈 제목은 한 줄로 명확하게
- 관련 파일 경로를 반드시 포함

## 제안 트리거
- 커맨드 실행 중 예상치 못한 동작을 감지하면:
  → "이 동작이 의도한 것인지 확인해주세요. 문제라면 /report-issue 로 기록하겠습니다"
- 사용자가 같은 불편을 2번 이상 언급하면:
  → "이 부분을 개선 이슈로 등록할까요?"
